# Commercial adapter and authorization

The OpenAI Responses adapter is implemented and covered by fake transport tests. No live provider validation or paid evaluation has been performed. Its default authorization and spending cap are zero. Supplying an API key alone does not enable requests.

Keep an approved configuration outside the public source tree. [provider.example.json](provider.example.json) is deliberately disabled and contains no prices. Before authorizing any live use, identify the provider account, permitted data classes, cumulative session spending cap, deployment model/capabilities and checked pricing. Configure `OPENAI_API_KEY` in the process environment; the GUI settings and source examples never store the secret. The account label is an authorization record, not an API account selector; the key's actual account must match the approved record.

Every commercial request requires all of: explicit commercial destination permission, `offline=false`, `private=false`, an authorized `identity.data_class`, positive request spending allowance, bounded deadline, enabled provider configuration, known versioned input/output pricing and a key. Offline and private restrictions take precedence. No unavailable local backend silently falls back to cloud or GPU.

Before opening HTTPS the adapter reserves a conservative UTF-8-byte input bound plus framing allowance and the full requested output allowance. This can reject prompts that would fit the provider tokenizer. It uses full configured input pricing even for cached tokens, so reconciled reported usage is a conservative upper cost bound rather than an invoice. Output usage includes reported reasoning tokens; details are retained. Unknown usage or a lost connection retains the reservation and reports unknown cost. A reported usage overrun disables the adapter for subsequent paid calls and requires account reconciliation. There are no automatic retries, including after rate limits. Closing a stream does not prove the provider stopped billing.

The session cap covers one adapter/process lifetime. Restarting creates a new session; it does not implement an account-wide or durable monthly ledger. Do not divide a single approved cap across multiple processes. Retained unknown reservations must be reconciled before a new paid session. Local computation and external validation costs remain unmeasured, not zero. Prompt/response logging is off in the provider transport. Evaluation artifacts intentionally retain prompts/results in a private run directory for grading.

The fixed endpoint is `https://api.openai.com/v1/responses`, with `store=false`, no tools and SSE text events. No custom base URL or redirect is accepted. Cancellation/deadline closes the client connection; billing may remain uncertain. The adapter emits typed errors without copying provider bodies that could echo prompts.

Checked 14 November 2026 against the official [streaming guide](https://developers.openai.com/api/docs/guides/streaming-responses), [Responses events reference](https://developers.openai.com/api/reference/resources/responses/streaming-events), and [GPT-6.1 Sol model documentation](https://developers.openai.com/api/docs/models/gpt-6.1-sol). The configured model name follows the existing project policy. The example deliberately uses a smaller deployment limit; current account access, deployment limits and prices must be independently confirmed. These documentation checks establish an API implementation reference, not project-specific provider quality or availability.

Within one GUI window the provider configuration is fixed after first selection. Equivalent JSON copies/path aliases share the existing ledger; Unload and local mode do not renew the cap. A changed authorization requires a newly reviewed session after reconciliation. This lock does not provide an account-wide ledger across separate processes.

Within one adapter, reservations and session disabling share a lock. Pending calls cannot submit using an authorization snapshot captured before a usage overrun disabled the session. Already submitted requests remain subject to uncertain billing and are not retroactively cancelled. Streamed text has a separate bounded client memory limit; exceeding it closes the client stream, retains its reservation and disables further paid submissions pending reconciliation. This memory bound is not a tokenizer count or invoice guarantee.
